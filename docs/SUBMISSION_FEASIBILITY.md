# Submission feasibility, per platform

Whether JobOrbit can submit an application to a given platform, and the evidence for the
answer.

**Rule applied.** "Supported" means a documented, authorized submission interface that an
individual candidate can legitimately use **without an employer-issued credential**. A
documented endpoint does not qualify if it requires an employer, partner or
organization-scoped credential. "Not found" means an authoritative statement was not
located; it is not a claim that no interface exists.

Every row is generated from the platform's own adapter at runtime — `GET
/api/autoapply/capabilities` — so this document cannot say one thing while the code does
another. `tests/test_compliance.py::test_no_real_platform_can_be_submitted_to` fails if any
row becomes supported without that test changing too.

**Result, API path: no real platform in scope can be submitted to through an API.** The only
API provider that can is a loopback test server this project runs itself.

**Result, browser path (added 21 Nov 2026):** with `JA_BROWSER_SUBMISSION_ENABLED=true`,
Greenhouse, Lever and Ashby become supported through a different route — not their
employer-keyed APIs, but the **public hosted application form** each posting already has,
filled in JobOrbit's own Chrome window exactly as a candidate would fill it by hand. See
[Browser submission](#browser-submission-greenhouse-lever-ashby) below. The matrix rows
underneath describe the API route and are unchanged.

## The matrix

| Platform | Automated discovery | Submission interface documented | Credential issued to | Candidate may use it | Must be completed by hand | Status |
|---|---|---|---|---|---|---|
| LinkedIn | no — User Agreement §8.2 | **not found** | none found | no | yes | `submission_not_supported` |
| Indeed | no — no jobseeker search API | yes, as a partner integration | approved vendor / ATS / employer | no | yes | `submission_not_supported` |
| Naukri | no — terms unverifiable | **not found** | none found | no | yes | `submission_not_supported` |
| Wellfound | no — terms prohibit automated access | **not found** | none found | no | yes | `submission_not_supported` |
| **Greenhouse** | **yes** — Job Board API (read) | yes | **employer** | no | yes | `submission_not_supported` |
| **Lever** | **yes** — Postings API (read) | yes | **employer** | no | yes | `submission_not_supported` |
| **Ashby** | **yes** — Posting API (read) | yes | **employer** | no | yes | `submission_not_supported` |
| **SmartRecruiters** | **yes** — Posting API (read) | yes | **employer** | no | yes | `submission_not_supported` |
| **Workable** | **yes** — widget API (read) | yes | **employer** | no | yes | `submission_not_supported` |
| Unrecognised form | n/a | n/a | n/a | no | yes | `submission_not_supported` |
| JobOrbit local test server | n/a | yes | candidate | **yes** | no | **supported, verified end to end** |

The finding worth stating plainly: **four of the five ATS providers do publish an
application-submission endpoint.** They are unusable here not because automation is
forbidden but because the credential belongs to the hiring company. That is a different
reason from LinkedIn's and Indeed's, and the adapters record which reason applies to which
platform.

## Evidence

### The five ATS providers — employer-held credential

Each quote is carried verbatim on the adapter and surfaced through the capabilities
endpoint.

**Greenhouse** — [Job Board API](https://developers.greenhouse.io/job-board.html)

> "Job Board data is publicly available, so authentication is not required for any GET
> endpoints. Only the application submission endpoint requires Basic Auth. The Job Board
> API Key must be Base64 encoded before it can be used to post applications."

and, on the same page:

> "the HTTP Basic Auth API token is a secret key. Any form posts should be proxied by your
> own servers. Any direct post to the /applications POST method would reveal your secret
> key to anybody that views source — which would be a very bad thing."

**Lever** — [Postings API: apply to a job
posting](https://github.com/lever/postings-api#apply-to-a-job-posting)

> "To use the POST API, you need an API key, which a Super Admin of your account can
> generate from your integrations settings page."

**Ashby** —
[`applicationForm.submit`](https://developers.ashbyhq.com/reference/applicationformsubmit)

> "Requires the `candidatesWrite` permission."

**SmartRecruiters** — [Application
API](https://developers.smartrecruiters.com/docs/application-api)

> "All endpoints are protected." An API key "can be generated by a user with Administrator
> access."

**Workable** — [careers page API
guide](https://help.workable.com/hc/en-us/articles/115012771647)

The `r_jobs` scope suffices to display openings — which is the feed this project reads for
discovery. A custom application requires `w_candidates` to "create candidates in
Workable", and tokens are generated by an Admin or Super Admin.

### LinkedIn — prohibited, and no candidate API found

LinkedIn publishes no candidate-side application API. Easy Apply is a first-party feature
of LinkedIn's own interface, not an interface offered to third-party software. User
Agreement §8.2:

> "Use bots or other unauthorized automated methods to access the Services, add or
> download contacts, send or redirect messages..."

(https://www.linkedin.com/legal/user-agreement, corroborated by
https://www.linkedin.com/help/linkedin/answer/a1341387)

### Indeed — an integration programme, not a candidate interface

Two independent findings, both pointing the same way.

From Indeed's legal terms (https://www.indeed.com/legal), fetched directly:

> "Use of any automation, scripting, or bots to automate the Indeed Apply process outside
> of Indeed's official vendors and tooling is prohibited."

From the Indeed Apply integration documentation
(https://docs.indeed.com/legal-terms/indeed-apply):

> "Indeed Apply can be provided by an ATS, an Employer directly, an Agency, or an Indeed
> approved 3rd party designated by the employer."

Third parties "must be vetted and approved by Indeed". So Indeed Apply is real and
documented, and every permitted integrator class is employer-side. It is not a self-serve
interface for an individual applying as themself.

### Naukri — unverifiable, so most restrictive

`https://www.naukri.com/termsconditions` did not yield readable authoritative text to a
programmatic fetch, and no official jobseeker developer programme or application API was
found. Since the rule above requires affirmative documented authorization, a missing
document does not establish permission. The adapter defaults to the most restrictive
setting and says so.

### Wellfound — no candidate API, and automated access restricted

> "use any automated system (including a spider, robot, or offline reader) to access the
> Site or Services"

> "If you are not a Candidate or an Employer, for example, if you are an external
> third-party recruiter or agency (including talent marketplaces), then you may not use
> the Site or the Services for any purpose."

(https://wellfound.com/terms)

The terms do recognise Candidates as a permitted user class, which is not the same as
authorizing automated application submission. No candidate submission API was found.

### Unrecognised forms

A job whose application URL matches no known provider routes to `unknown`, which is also
unsupported. An unrecognised form is precisely where automated filling would guess, so
nothing is attempted and the page is opened for you.

## The one verified end-to-end integration

`tests/support/application_server.py` serves a real multi-step application form over
loopback with a synthetic account. `app/submission/local_test.py` applies to it for real:
reads the form, maps verified answers onto it, uploads the resume as `multipart/form-data`,
commits, then re-reads the application independently to confirm it exists.

Two guards stop it becoming a route to real employers:

1. **Unregistered unless configured.** `JA_LOCAL_SUBMISSION_BASE_URL` is empty by default,
   so the registry exposes no supported target and a normal installation submits to
   nothing at all.
2. **Loopback only, enforced at construction.** Pointing it at `boards.greenhouse.io`,
   `example.com`, a private address or a public IPv6 address raises `NonLoopbackTarget`.

Both are asserted by test.

## What a run reports, and what it does not claim

Authorising 100 attempts authorises 100 *attempts*. These figures are reported separately
and never summed:

| Figure | Meaning |
|---|---|
| `eligible_count` | matched the run's scope |
| `prepared_count` | a complete application exists — **not sent** |
| `confirmed_count` | a provider acknowledged receipt and returned a confirmation id |
| `blocked_count` | a required answer is missing or unverified |
| `needs_user_count` | a CAPTCHA, MFA challenge or expired session needs a person |
| `unsupported_count` | the platform permits no automated submission |
| `unknown_count` | the request left this machine and nothing came back |
| `failed_count` | the attempt provably never arrived |

In a default installation `confirmed_count` is **zero on every run**, because no real
platform authorises candidate submission. That is the product being accurate.

`unknown_count` is the figure worth understanding. It means a submission may or may not
exist on the employer's side, so it is **never retried automatically** — retrying an
unknown outcome is how one application silently becomes two. Those rows are surfaced for
you to check by hand.

## Credentials

`app/submission/credentials.py` reads a provider token from the process environment at the
moment of use. It is never written to the database, never stored under `var/`, never
returned in an API response, and `Credential.__repr__` redacts it so a traceback cannot
leak it. A variable naming a password, a cookie or a session id is refused outright:
reaching a platform account is done by you signing in to your own browser, not by this
project holding a secret. No employer API secret is reused, and no web form is automated
as a substitute for an authorized interface.

## Revisiting a row

Change one only after official documentation affirmatively establishes a candidate-facing
submission path and its credential model. The steps are: record the citation on the
adapter, change the expected set in
`tests/test_submission_engine.py::test_the_only_supported_target_is_the_local_test_server`,
update `test_no_real_platform_can_be_submitted_to`, and add the evidence here. The design
makes that deliberate rather than accidental.


## Browser submission (Greenhouse, Lever, Ashby)

Implemented in `app/submission/browser_ats.py`, `app/browser/`. Off unless
`JA_BROWSER_SUBMISSION_ENABLED=true`; `tests/test_browser_submission.py::test_browser_targets_exist_only_when_switched_on`
pins the supported set to exactly these three when on, and to nothing when off.

| Provider | Form read from | Invisible CAPTCHA observed (Nov 2026) | Confirmation signal |
|---|---|---|---|
| Greenhouse | `job-boards.greenhouse.io/<board>/jobs/<id>` | reCAPTCHA Enterprise | redirect to `/confirmation`, "Thank you for applying" |
| Lever | `jobs.lever.co/<company>/<id>/apply` | hCaptcha | redirect to `/thanks`, "Application submitted" |
| Ashby | `jobs.ashbyhq.com/<org>/<id>/application` | reCAPTCHA Enterprise | in-place "Thank you for applying" |

What the browser path will not do: log in anywhere on the user's behalf, solve or dismiss a
CAPTCHA, hide that the browser is automated, tick a declaration without the user's own
answer to that exact text, answer a question nothing on file answers, or retry an outcome it
could not read. A visible challenge leaves the tab open and the attempt `requires_user_action`.

Verified: 16 browser tests drive real headless Chrome against loopback copies of the three
forms (`tests/support/ats_forms.py`), and the adapter's form reader was run read-only (no
typing, no upload, no submit) against six live postings — Groww (Greenhouse), CRED (Lever),
Atlan and Sarvam (Ashby) — which found the resume upload on all six and surfaced three
real-markup issues that were then fixed (consent choices labelled "Phone", phone-country
option lists, unlabelled type-ahead inputs). **No application has been submitted to a real
employer by any test.**
